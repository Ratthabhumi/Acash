## 5. D1 — Runtime Identity & Provenance

`INFERENCE`: The manifest already binds strategy identity (strategy_id/version),
revision identity (`git_commit`), configuration identity (`config_hash`,
`strategy_config_hash`), and journal identity (`journal_final_hash`). For a
deployed container, the audit found the **runtime** identity was not yet bound
at all.

`DESIGN DECISION` (D1.1): Distinguish three provenance layers and treat them as
distinct, non-interchangeable claims:

| Layer | Claim | How it is established |
| :- | :- | :- |
| IMAGE IMMUTABILITY | The bytes at a container image path are fixed. | Pinned image **digest** (e.g. `sha256:…`) in the compose service image reference; never `:latest`. |
| CODE IDENTITY | The image bytes correspond to a known ACASH source revision. | Build chain bookkeeping: git commit → build → digest; the window manifest records both `source_git_commit` (ACASH repo) and the digest actually run. |
| RUNTIME PROVENANCE | The image identity that was *configured* is the one that actually ran during a **runtime segment** of the observation window. | Container identity (`container_id`) + `image_digest` observed at each segment open/close, `docker inspect` verification at segment open/close, Watchtower exclusion, host identity, start/stop event attestation. |

`DESIGN DECISION` (D1.2): A single `container_id` for the entire window is NOT
required. Runtime identity is modeled as an ordered list of **runtime segments**
within the window (see [§8](#8-d3--session--observation-window-model) /
[§9](#9-window-manifest-schema)):

```
Observation Window
  ├── Runtime Segment A
  │     ├── segment_id, start_utc, end_utc
  │     ├── container_id
  │     ├── image_digest
  │     ├── git_commit (ACASH build source revision)
  │     ├── image_reference (registry/repo:tag@sha256)
  │     └── member session(s) (session_id)
  ├── Runtime Segment B
  └── Runtime Segment C
```

Each segment carries its own container identity, digest, and git commit, plus a
per-segment `watchtower_exclusion_verified` flag and the `deployment_interlock`
record (see [§6](#6-d2--gitops-deployment-interlock-high-priority)). A window
that intentionally spans multiple containers is therefore representable without
contradiction.

`DESIGN DECISION` (D1.3): **A runtime identity change is NOT automatically a
provenance violation.** It is a violation only when it is unrecorded or
unattributable. Policy (fail-closed; mirrors AGENTS.md rule 3):

| Situation | Classification |
| :- | :- |
| Intentional sealed-session deployment transition (governed path — D2.5, §16), recorded as a runtime transition | RECORDED TRANSITION — admissible |
| Crash/restart, observed and recorded as a runtime transition (`--resume`/`recover()` reseals; segment record written) | RECORDED TRANSITION — admissible after validation |
| Silent container replacement during an OPEN window with no transition record | PROVENANCE VIOLATION — window inadmissible |
| Ambiguous provenance (a segment missing `container_id`, `image_digest`, `git_commit`, or `transition_reason`) | AMBIGUOUS — fail closed; window inadmissible until resolved |

The window **must not** be admissible as evidence if any violation or ambiguity
remains at seal time.

`DESIGN DECISION` (D1.4): The engine today accepts `--git-commit "unknown"`.
For paper-window evidence, `git_commit = "unknown"` in the window manifest is a
fail-closed violation, not a warning. The deploy harness (CI) must supply the
real commit, and the window manifest validator must reject `"unknown"`.

`DESIGN DECISION` (D1.5): Every runtime transition (segment open/close/replace)
is written as a transition record in the window manifest `runtime_segments` list
with `transition_reason`, `transition_recorded_at_utc`, and
`transition_recorded_by`. The validator requires each segment boundary to have
exactly one attributable reason. `TEST REQUIRED` (G12/G13 in
[§21](#21-acceptance-gates)).

`INFERENCE`: Recorded `data_source`, `instrument_universe`, `market_domain`
already satisfy single-authority provenance of the market-data claim.

## 6. D2 — GitOps Deployment Interlock (High Priority)

`FACT`: Ansible `01_deploy_homelab.yml` runs `docker compose up -d --pull always
--remove-orphans`; any push to main triggers it on the self-hosted runner. With
`restart: unless-stopped` and `:latest`, a deploy during an active observation
window would **silently re-create the evidence-producing container** without a
recorded runtime transition — the condition D1.3 classifies as a provenance
violation.

`DESIGN DECISION` (D2.1): Introduce a two-file deployment interlock whose
authority is a single marker the engine owns, stored on the **single persistent
mount root** (`/data/docker/acash/`, see [§10](#10-runtime-layout--storage-partitioning)):

- Marker: a window-state file under `/data/docker/acash/windows/<window_id>.state.json`
  with states `OPEN`, `SEALED`, `VOID`.
- `OPEN` means one or more sessions belong to an unsealed window → **deploy of
  the paper service is BLOCKED**.
- `SEALED` means the window was explicitly/regularly closed → deploy allowed.
- `VOID` means explicit human-issued void (used only via a governed procedure).

Interlock state machine [DESIGN DECISION]:

| Current | Event | Transition | Guard |
| :- | :- | :- | :- |
| QUIESCENT | human/CI issues window open | → OPEN | Validated D1 config (digest pinned, labels present), `git_commit != "unknown"`, capacity record present |
| OPEN | deployment pipeline targets paper service (automatic/CD) | `BLOCKED` (no transition) | Require SEALED or VOID before proceeding |
| OPEN | governed operator/CI runtime transition (stop → replace → resume) | new Runtime Segment opened (window stays OPEN) | Transition record written FIRST (D1.5); digest pinned; attributable |
| OPEN | window expiry or explicit close | → SEALED | All member sessions sealed; integrity checks PASS |
| OPEN/SEALED | human-issued void (governed procedure only) | → VOID | Requires explicit governor sign-off; journaled |
| SEALED | deploy pipeline | allowed | — |

`DESIGN DECISION` (D2.2): The deployment pipeline must read the interlock before
`compose up`; if any window is `OPEN`:
- **automatic/CD deploys** of the paper service are **BLOCKED** (compose up
  aborts or skips only the paper service) and return a non-zero status — no
  silent replacement is possible. Which stance (abort vs skip) is an
  `OPEN DECISION` (O4).
- a **governed runtime transition** (operator- or CI-initiated stop → replace →
  resume) is permitted **only** through the transition channel: it MUST first
  write the new runtime segment record (D1.5) with a permitted reason; without
  a written transition record the pipeline stays BLOCKED. The transition records
  the old and new `container_id`/`image_digest` as separate segments with
  attributable reasons, preserving RUNTIME PROVENANCE (D1.2).

`INFERENCE` (D2.3): Because the interlock defaults to BLOCKED for automatic/CD
deploys, silent container recreation during OPEN is prevented; the only safe
leaves are: no active window, or a SEALED/VOID window. This neutralizes the
`--pull always` hazard for the paper service (R6 in [§24](#24-risk-register)).
Governed runtime transitions (D2.2) are the only way to rotate containers mid-
window, and they require an attributable written record (D1.5).

`DESIGN DECISION` (D2.5): The **governed runtime transition channel** (D2.2)
is the ONLY way to rotate the paper container while a window remains OPEN.
The channel requires: (a) the transition record written FIRST (D1.5), (b)
a permitted transition reason (sealed-session deployment; operator-controlled
stop/resume), and (c) digest pinning intact post-transition. Unrecorded or
unpermitted rotations remain BLOCKED.

`DESIGN DECISION` (D2.4): Watchtower is *also* part of the interlock surface:
the paper container gets the supported opt-out label
`com.centurylinklabs.watchtower.enable=false` (C2 — not a reuse, it is new usage
of a supported mechanism) AND a pinned digest so Watchtower cannot pull a new
image at 04:00 even if the label were misapplied. `TEST REQUIRED` for the label
honor in [§21](#21-acceptance-gates) G1.

## 7. Deployment Flow & Version Control

`FACT`: The only supported deploy pattern in this repo is a service entry in
`docker/compose.yaml` (GitOps single stack), materialized by the Ansible copy +
`compose up`. There is no image registry in the repo.

`DESIGN DECISION` (D7.1): The paper image reference in compose must be the
registry/repo with an explicit `@sha256` digest and a named tag for
readability (e.g. `acash:paper-v1@sha256:…`), never `:latest`.

`DESIGN DECISION` (D7.2): Build and provenance bookkeeping:
- Build produced by CI from the ACASH repo at a known commit (`FACT`: `ci.yml`
  runs on the ACASH side; HomeLab has no build step for ACASH).
- The mapping commit → digest is recorded as data in the ACASH repo (or the
  window manifest authoring tool), so RUNTIME PROVENANCE can be re-asserted later.

`DESIGN DECISION` (D7.3): Version lifecycle for paper image: tag `paper-vN`; bump
N is a human decision after review; rollback = redeploy previous tag/digest
(pattern exists in compose: move tag, `compose up -d`). Digest history retained;
no auto-update ever for the paper service.

`INFERENCE` (D7.4): Because deploy recreates containers in dependency order
(not atomically), the paper service must not depend at runtime on sidecar
recreation ordering — it is a self-contained poll loop with no intra-stack
dependencies (`FACT`: engine stands alone; feeds are external HTTPS).

## 8. D3 — Session / Observation Window Model

`FACT`: The engine's unit of record is a **session** (`session_id`, journal,
snapshots, sealed manifest). The CLI `run`/`resume`, `status`, `integrity`,
`review` all address a single session. There is no concept of a window today.

`DESIGN DECISION` (D3.1): Introduce an **observation window** as the
evidence-of-record aggregate above sessions. A window:
- has one canonical `window_id` and one **window manifest**;
- owns a calendar span (e.g. the 3-month Paper Review window) and a recording
  target (e.g. one instrument UNIVERSE BTUSDT? — see below);
- aggregates **one or more sessions**, each with its own `session_id`, journal,
  snapshots, and sealed session manifest — the engine's session model stays
  unchanged;
- holds the D1 runtime-provenance record for the whole span **as an ordered list
  of runtime segments** (D1.2); one window may intentionally span multiple
  containers across segments;
- is SEALED by the window authoring step that pulls each member session's
  sealed manifest + hashes + `integrity`/`review` output into the window
  manifest.

`INFERENCE` (D3.2): A single session_id for a 3-month uninterrupted run is
brittle (any restart mid-window is then forced into the same session). The
window model decouples "the period of evidence" (window) from "the unit the
engine stores" (session). This is why the design does not mandate one
uninterrupted session (correcting the audit's single-session phrasing).

`INFERENCE` (D3.2.1): Sessions within a window **may intentionally run in
different containers/runtime segments** (D1.2). This is the expected pattern
under the runtime-segment model and is NOT a provenance violation on its own —
each segment carries its own attributable identity (D1.3/D1.5).

`DESIGN DECISION` (D3.3): Window formation rules:
- A window's member sessions are started and stopped by the window supervisor
  (a small harness around the engine CLI — design-level; not implemented).
- Calendar-day boundary policy is an `OPEN DECISION` (new session per UTC day is
  the default working proposal, because it bounds reseal/recovery scope per day).
- Any restart (`--resume`) stays within its session; sessions are appended to the
  window as they seal.
- The window manifest references each member by `session_id` + `journal_final_hash`
  + `manifest_hash`, so single-authority hashing is preserved per session.

`DESIGN DECISION` (D3.4): Instrument/universe of the window is a window-level
recording target, not per-session free choice: one `window_id` records a fixed
`instrument_universe` and `data_source`; all member sessions must declare the
same values (validator rejects mismatches). `DESIGN DECISION` (fail-closed).

`INFERENCE` (D3.5): With windows, the 3-month evidence window maps 1:1 to one
window manifest; the 7-day backup retention becomes a *per-session* retention
question, which D7 ([§17](#17-d7--backup--restore-evidence-policy-policy-first))
answers differently for operational logs vs evidence-of-record.

## 9. Window Manifest Schema

`DESIGN DECISION`: The window manifest is a **new artifact**, distinct from
`PaperSessionManifest`. Proposed canonical fields (all to be given a single
authoritative computation point in implementation):

| Group | Fields |
| :- | :- |
| Identity | `window_id`, `window_manifest_id`, `window_open_utc`, `window_seal_utc`, `author` (harness/operator), `created_by_version` |
| Recording target | `data_source`, `instrument_universe`, `market_domain`, `timeframe`, fixed per D3.4 |
| Member sessions | ordered list of `{session_id, journal_hash, session_manifest_hash, sealed_at_utc}` + `aggregate_event_count` |
| Runtime provenance (D1) | `host_identity`, `runtime_segments` (ordered list of `{segment_id, start_utc, end_utc, container_id, image_reference, image_digest, git_commit, member_session_ids, transition_reason, transition_recorded_at_utc, transition_recorded_by}`), `watchtower_exclusion_verified`, `deployment_interlock` record |
| Time integrity (D4) | `clock_source_utc` attestation, `max_observed_skew_ms` (per D4.3), `ntp_drift_log_ref` |
| Feed policy (D6) | `feed_failure_events` (count), `halted_reason_chronology` (list), `auto_recovery_used: bool` (must be False unless a future validated decision) |
| Evidence classification | `operational_vs_evidence_classification` (see D7), `evidence_status`: `OPEN`, `SEALED`, `VOID` |
| Sealed aggregates | `total_sessions`, `first_session_start_utc`, `last_session_end_utc`, `aggregate_reconciliation_status` |
| Integrity | `window_manifest_hash` (SHA-256 over canonical fields excluding itself) |

`INFERENCE`: Every timestamp is UTC; every hash is SHA-256 via the existing
canonical serializer (no new hash utility — search-before-inventing holds).
`DESIGN DECISION`: window manifest seal is a fail-closed validator: any blank
provenance field (e.g. a runtime segment missing `image_digest`,
`transition_reason`, or `git_commit`) → seal fails.

## 10. Runtime Layout & Storage Partitioning

`FACT`: HomeLab convention mounts persistent app data under
`/data/docker/<service>/`. `auto_backup.sh` tars `/data/docker` and **excludes**
`*/logs/*`.

`DESIGN DECISION` (D10.1) — storage layout under `/data/docker/acash/`:

| Path | Content | Backup class (see D7) |
| :- | :- | :- |
| `/data/docker/acash/windows/<window_id>.manifest.json` | window manifest (evidence) | EVIDENCE-OF-RECORD |
| `/data/docker/acash/sessions/<session_id>.journal.jsonl` | session journal (evidence) | EVIDENCE-OF-RECORD |
| `/data/docker/acash/sessions/<session_id>.snapshots.jsonl` | session snapshots (evidence) | EVIDENCE-OF-RECORD |
| `/data/docker/acash/sessions/<session_id>.manifest.json` | sealed session manifest (evidence) | EVIDENCE-OF-RECORD |
| `/data/docker/acash/logs/` | operational logs only | OPERATIONAL (excluded from evidence backup, matches engine's exclusion) |
| `/data/docker/acash/review/<window_id>/` | review-package output bundle | OPERATIONAL (regenerable) |

`DESIGN DECISION` (D10.2): ownership — a non-root paper UID with a
container-writable mount for the whole `/data/docker/acash/` tree (matches the
repo's chown-helper pattern; exact UID assignment is implementation detail —
`OPEN DECISION` until capacity/UID census review).

`DESIGN DECISION` (D10.3): **single persistent mount root** — the container mounts
`/data/docker/acash` (host) → `/data/docker/acash` (container), the complete
tree in D10.1. There are **no multiple unrelated mounts**. All of:
- `windows/` (interlock state + window manifests),
- `sessions/` (journal/snapshots/session manifests — the evidence tier),
- `logs/` (operational logs, excluded from backup per engine convention), and
- `review/` (review-package output, regenerable)

are logical subdirectories of the **one mounted root**. Ownership is by component
responsibility, not by separate mounts.

The engine CLI receives `--storage /data/docker/acash/sessions` — a *subdirectory
of the mounted root*, NOT a separate mount — so session artifacts land on the
evidence tier. The window supervisor / interlock owns `windows/` under the same
root, co-located with the session evidence. The storage root survives container
recreation (G14 in [§21](#21-acceptance-gates)).

`INFERENCE` (D10.4): Estimated volume per day is the subject of D5
([§12](#12-d5--resource--storage-budget)); no bytes/day figure is asserted here.

## 11. D4 — Time Integrity

`FACT`: The engine records `received_at_utc` (wall-clock ingestion) and
`timestamp_utc` (market event close) per bar, and computes
`data_age_ms = received_at - event_time`; freshness is a gate. `UNKNOWN`: the
host's NTP discipline is **not declared in the repositories**.

`DESIGN DECISION` (D4.1): Wall-clock → integrity rules for windows:
- Container runs with `TZ` normalized so application timestamps are UTC, matching
  the engine's UTC normalization. (Engine already forces UTC in validators.)
- A clock-skew tolerance value, if ever adopted, remains an `OPEN DECISION`
  (`TEST REQUIRED`; see O7). It is not settled by this document and is not
  silently locked to any numeric value.

`DESIGN DECISION` (D4.2): The window manifest records a **clock attestation**
in the D1/D4 record: the host clock/NTP attestation *supplied by the
infrastructure layer* (D4.5 below), captured at each runtime segment
open/close, and the max `data_age_ms` observed across all member sessions. A
window whose max age repeatedly exceeds the freshness gate is flagged for
review; it does not silently upgrade or downgrade evidence.

`DESIGN DECISION` (D4.3): Distinguish monotonic identity from wall-clock: session
append-hash chain and `_seen_feed_source_ids` depend on engine-internal
monotonic order, not wall clock. Wall clock is only used for freshness and window
span. Keep that separation explicit in the window authoring report so a clock
jump cannot corrupt hashes.

`INFERENCE` (D4.4): Because the freshness gate already refuses stale bars
(fail closed), the primary remaining time-integrity risk is **host clock skew
mislabeling window span**, which D4.1/D4.2 address via attestation, not by
altering engine behavior.

`DESIGN DECISION` (D4.5) — explicit ownership boundary for time integrity:

| Layer | Responsibility | Owner |
| :- | :- | :- |
| Host system clock + NTP sync | Physical clock discipline on the HomeLab node | **HomeLab / infrastructure** |
| Host clock attestation | Host-level NTP/clock status supplied to workloads | **HomeLab / infrastructure** |
| Container/application UTC timestamps | `received_at_utc`, `timestamp_utc`, `data_age_ms`, journal/event timestamps | **ACASH container** |
| Association of infra attestation with the window | Recording the host-provided clock attestation in the window manifest at segment open/close (D4.2) | **ACASH window authoring step** |

Host clock/NTP attestation is *supplied by the infrastructure layer*; ACASH
records and associates that attestation with the observation window. The
non-root ACASH container must NOT be required to directly access privileged
host NTP state.

## 15. D6 — External Feed Failure Policy

`FACT`: On connect/poll failure the supervisor halts (`halted=True`,
`halted_reason`), journals `FEED_DISCONNECTED`, and refuses further decisions
until an explicit `--resume`/`reconnect()`. Reconnect inside a session is
explicit by design — there is **no automatic retry** today.

`DESIGN DECISION` (D6.1): **Fail-closed is the default and the only allowed
default in this design.** No bar is admitted, no decision is produced, while the
feed is halted/stale/disconnected.

`DESIGN DECISION` (D6.2): On an identified disconnection, the supervisor's
behavior is already correct: record, halt, journal. The window authoring step
accounts failures in the `feed_failure_events` and `halted_reason_chronology`
records (D1/D4 record).

`OPEN DECISION` (D6.3): Automatic recovery (periodic re-connect retry) is NOT
adopted by default. It may only become a design decision after a validated
"auto-recovery" design that preserves the fail-closed and no-silent-bar-admission
invariants. Until then, recovery is operator-issued `--resume`.

`TEST REQUIRED` (D6.4): egress from `homelab_proxy` to `api.binance.com`, stale
bar rejection under `max_market_data_age_ms`, duplicate-feed protection across
restarts — see [§21](#21-acceptance-gates).

## 16. Shutdown & Graceful-Stop Policy

`FACT`: `cli.py` has **no signal handling**. A default `docker stop` sends
SIGTERM; Python's default kills the process, leaving the session manifest
unsealed. Today the operator must `--resume` to reseal (recovery path exists and
is tested).

`DESIGN DECISION` (D16.1): Add a bounded (SIGTERM/SIGINT) handler to the run
loop that performs `disconnect()` + `stop()` (seal manifest) within a grace
window (e.g. ≤ 10s) — a future ACASH change. Until it exists, the interlock D2 +
exclusion label + pinned digest make an unsealed-mid-window re-creation
extremely unlikely, but not impossible.

`DESIGN DECISION` (D16.2): Even with the handler, every `docker stop` during an
OPEN window closes a runtime segment and is a **runtime transition**: it must be
recorded in the window manifest (`runtime_segments` + transition reason per
D1.5/§9), never silent.

`TEST REQUIRED` (D16.3): SIGTERM graceful-stop test — journal intact, manifest
sealed, resume reseals if not (G2 in [§21](#21-acceptance-gates)).

## 17. D7 — Backup / Restore Evidence Policy (Policy First)

`DESIGN DECISION` (D7.1) — classification of artifacts, drawn from the audit's
distinction:

| Class | Artifacts | Backup policy |
| :- | :- | :- |
| OPERATIONAL LOGS | `logs/**`, review bundles, Prometheus series, VM data | existing engine retention (7d tar band, VM 1-month); regenerable |
| EVIDENCE-OF-RECORD | session journals/snapshots/sealed manifests, window manifests | entire 3-month evidence window + margin; must survive host loss where the engine guarantees it can |

`DESIGN DECISION` (D7.2) — the 3-month evidence window **cannot** rely on the
default 7-day retention band. The design reuses the existing engine
(`auto_backup.sh` tar of `/data/docker`) and **extends** it with an evidence
retention band:
- evidence artifacts (path band under `/data/docker/acash/{windows,sessions}/`)
  are kept for the full window + margin (e.g. 3 months + 1 week margin) rather
  than 7 days;
- OPERATIONAL logs keep today's exclusion policy.

`OPEN DECISION` (D7.3): scheduler for the extended band is not declared in repo
today (`FACT`/`UNKNOWN`). Where/when the backup runs (host cron invisible to
repo, Ansible-managed systemd timer, or weekly ops step) is explicitly left open;
retention policy is fixed by D7.1/D7.2.

`DESIGN DECISION` (D7.4): Same-disk backup (`/data/backups` on the same HDD) does
not protect against physical device loss. Policy: evidence-of-record must have a
**second copy eventually** (offsite/Restic is Sprint-15 planned, not done
`FACT`); until then the design states plainly that the evidence lives on one
physical device and the restore drill (not hardware redundancy) is the operative
guarantee. This is stated as a residual risk, not hidden.

`TEST REQUIRED` (D7.5): restore drill — `auto_backup.sh` → extract to
`/data/docker/acash/...` → `status`/`integrity`/`review` PASS on restored
artifacts; window manifest seal still validates (G4).

## 18. Restore & Disaster Recovery Procedure

`DESIGN DECISION` (D18.1): restore procedure design:
1. Stop the paper container (interlock: only after window SEALED/VOID).
2. Restore evidence band from the (extended) backup archive into
   `/data/docker/acash/`.
3. Re-run `acash paper status`/`integrity`/`review` on every restored session; all
   must PASS; window manifest re-validates.
4. If any session fails integrity after restore → mark window `VOID` or re-run —
   never silently accept.

`DESIGN DECISION` (D18.2): The window manifest records `restored_at_utc` +
`restored_from_backup_ts` when a window has been restored (auditability).

`INFERENCE` (D18.3): because journals are append-only with a hash chain and
snapshots are immutable per event, restores are verifiable against
`journal_final_hash` — the restore drill is the mechanism that proves the chain
survives archive round-trip.
